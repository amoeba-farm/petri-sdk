# Mainnet integration

Import browser-safe `MAINNET_PROFILE` from `ameba-sdk/mainnet/profile`. Its release label is `spread-mainnet-20260916`, read profile is `ameba-spread-v2-mainnet-b66fbc8f`, and `governance-gate-v1` describes the governance ABI, not activation.

Server consumers import `createMainnetSdkAdapter` and `observeMainnetDeployment` from `ameba-sdk/mainnet`. Supply a finalized `Connection` to the private Mainnet Helius endpoint. There is no default or public fallback. The observer verifies genesis, Program/ProgramData linkage, authority, deployment slot, exact executable bytes and canonical gate. Its result reports gate status separately from readiness.

`createMainnetSdkAdapter({ connection, photonConnection? })` composes the existing current reader methods with Mainnet deployment attestation. Their retained RC44 deployment field identifies decoder semantics only; the adapter's `profile` and `observeMainnetDeployment()` identify the actual production deployment. Old `/protocol` deployment receipts remain historical Devnet records.

Production G3 paths are `resolveG3UserIntent(owner, operation, request, floor?)`, `prepareG3UserOperation(ownerPublicKey, input, floor?, lookupTable?)`, and `revalidateG3UserOperation(plan, signedBase64)`. Receipt and order operations retain host business admission. Preparation requires a freshly observed Active gate and exact Mainnet executable; plans bind the production profile and source, and revalidation rechecks epoch, executable, transaction bytes and lifetime. These methods do not sign or submit. Existing legacy generic write methods remain unavailable under the G3 package; they are not automatically migrated. The Rust G3 reconstruction profile remains local-test-only.

`ameba-sdk/g3/browser` exports `materializeMainnetG3Plan({ connection, plan, expected: { owner, operation, request } })`. Retain `expected` from the original UI request. The browser uses only `https://api.amoeba.farm/rpc`, re-observes Mainnet genesis/executable/gate, resolves fresh canonical accounts, and reconstructs the whole transaction. It compares every message byte with the prepared plan, including compute budget, amounts, direction, price limit, account metas and recipients. The result includes `transaction`, `messageBytes`, plan identifiers and `validateSignedTransaction(signedBase64)`. It never obtains a private Helius endpoint or signs.

For the existing swap UI, the semantic order request is `{ kind: "swap", market, direction, amountIn, minimumAmountOut, limitPriceAtoms, deadlineTs }`, with canonical decimal strings. Both browser and server derive the account map and read both order-book linked lists from canonical PDAs; no caller-supplied metas are needed. Routes exceeding eight reserve pages or 24 order records fail closed. Large transactions require an existing reviewed lookup table; missing markets, books, accounts or lookup tables remain bootstrap prerequisites.

G3 layout selection is explicit: Mainnet market reads require the 279-byte Market (six fee bytes removed), while historical reads retain the 285-byte decoder. G3 fees project as zero. The semantic order resolver uses the 364-byte order-enabled pool, native V3 sleeve, 230-byte book and 137-byte records. Focused fixtures cover nonempty market decoding, canonical swap resolution, exact economic encoding, Mainnet browser reconstruction and intent mutation rejection. Synthetic Active-gate tests do not establish live activation.
